# Luna 复杂任务诊断：结果与改进

2026-10-23 完成。本轮没有证明 OwnVoice 优于普通提示加完整检查清单。六个留出任务中，Luna 的整份成品偏好为：普通提示 1、清单 3、OwnVoice 0、平局 2。这只是同型号评审的小样本观察，不能解释为人类用户胜率。

## 实际完成范围

新增任务额度用了 **59/60**：1 次预检、36 次初稿、12 次等额代码反馈修订、10 次盲评；无运行失败和重试，剩余 1 次未使用。旧账本保留，累计 **239/240**。这里的单位是启动的 CLI 任务，不是不可见的底层 API 重试数。

所有新生成和模型评审均显式请求 **gpt-6-luna / medium**，没有继承默认型号或回退。59 个返回事件均未提供型号元数据，故证据是显式 CLI 路由，而非返回型号确认。旧轮仅知道使用了 Codex CLI，不能追认其实际型号。

十二个新合成任务分为开发 6 个、留出 6 个；每阶段各有中英文代码、科研、邮件任务。三组均获得相同事实、样例、约束、输出格式及反馈预算：普通提示、普通提示加完整清单、OwnVoice。未读取项目作者的私人档案。风格由无关事实的样例表达，不再直接给出变量长度、句数等答案式规则。

代码跨两个模块，涉及关键字参数、别名、异常、None/NaN、零值、顺序、版本覆盖、输入不变及单位边界。科研包含纠正版替代初稿、单位转换、区间跨零、指标权衡和未测量值。邮件包含旧线程、当前指令、上下文金额、收件人职责与时区转换。

可复核的差异包括：普通提示中文留出邮件将“期限前回复是否有空”写成“期限前帮忙查看”，结构化账本却仍写确认时间；英文科研增加了来源没有注明的“mean”。Luna 标出了这两处。OwnVoice 的英文科研在开发和留出均多了一个 JSON 结束括号；开发英文邮件还把 artifact 改成 draft。Luna 抓到了无效 JSON，却漏掉了字段改名，说明评审也有盲点。

文字严格探针的原始通过数为：开发 2/6、2/6、3/6；留出三组均 2/6。**这些数不能作为语义正确率或优势证据。** 它混入未明确要求的金额嵌套字段、固定日期字符串和正文引用位置，完整问题见 [测量审计](luna-v2-measurement-audit.md)。原始分数保留，不事后改规则制造一个有利的“纠正通过率”。

## 改了什么，效果如何

开发结果后只做了一次候选修改：三种成品技能明确优先遵守任务输出格式与原字段名，验证说明仅放入允许的字段，有解析器时实际检查。详见 [0.1.2 修改记录](../docs/CHANGES_0.1.2.md)。旧候选、输入哈希和原输出均保留；留出生成前冻结新版，中途未查看输出或调参。

留出英文邮件保留了 artifact，但英文科研仍有无效 JSON。**这次文字规则补丁不够可靠，不能称为修复成功。** 两阶段任务不同，也不能用缺失字段数的变化估计补丁因果效果。留出之后没有继续修改技能或重跑答案。

## 成本与价值判断

| 每阶段 8 次生成及修订的提示字符合计 | 普通提示 | 完整清单 | OwnVoice |
| --- | ---: | ---: | ---: |
| 开发 | 29,365 | 42,687 | 62,361 |
| 留出 | 28,506 | 38,228 | 64,196 |

OwnVoice 的提示字符约为普通提示的 2.12 倍和 2.25 倍，却没有相应的质量优势证据。CLI 报告的输入、缓存、输出 token 和耗时均另存于 [汇总 JSON](luna-v2.json)。CLI 固定开销和缓存顺序影响这些值，不能由字符数直接推算价格，也不能用本轮耗时宣称某组更快。

目前能确认的产品功能是把约束、检查资源和可选档案封装成可安装、可复用的入口。是否减少遗漏、减少用户重复输入、节省修改时间，仍未测得。只在提示中重复这些提醒，尚不足以形成有说服力的质量差异。因此当前定位维持技术预览，不宣传“比好提示更好”或检测器结果。

## 后续工作的具体方向

1. 优先把输出格式、接口和行为约束接到可执行的交付检查；失败时阻止交付并给出精确差异。解析失败不能靠再加一句“请检查”保证解决。这个机制也必须向清单对照提供等额工具，才能检验技能的组织价值。
2. 风格适配需要同一复杂任务交换两套风格样例，检查输出是否随样例改变，同时保住内容。增加多文件真实修改和多轮反馈任务，避免原样复制参考实现即可通过。先明确嵌套 schema，再冻结检查；未知的风格偏好仍保持未知。
3. 再做独立使用者盲评与实际修改时间比较，分别记录采用意愿、缺陷和成本。让真实用户选择风格，不能用 Luna 的空行偏好代替用户体验。若仍与完整清单持平，就保留为轻量规则工具，减少无效指令体积。

这三项是待实施验证方向，本轮没有声称已完成。完整基线信息、预算与输入冻结规则见 [运行前协议](../evals/luna_v2/PROTOCOL.md)，v1 短板分析见 [审计](../evals/luna_v2/ANALYSIS.md)。

软件验证：39 项单元测试和四项技能包静态检查通过；这些验证工具和安装边界，不证明风格优势。原始输出、本地三组对照页、盲评映射及冻结清单保留在忽略的 .local/，未发布到 GitHub。
